# Relay v2 security boundaries

Status: Milestones 2 through 2.3B are implemented and tested, including the approval-bound Codex CLI process boundary, the evidence-bound review foundation, a real, read-only local Claude Code CLI reviewer (see `docs/CLAUDE_REVIEWER.md`), and a fourth hardening pass adding a mandatory artifact-store requirement, a coordinated total material byte budget, and an enforced category-specific truncation policy for AUTHORITATIVE reviews (see "Milestone 2.3B corrective pass" below). No Anthropic API/MCP/deployment integration is present — Claude is invoked only as a local subprocess, never an API.

## Local boundary

- `/v2` and `/api/v2` remain feature-isolated.
- Mutations require loopback headers, same-origin classification, and matching CSRF cookie/header.
- Execution SSE additionally checks project/session ownership and reads only redacted persisted events.
- Execution cancellation requires `projectId`, verifies project/session ownership before cancellation, and does not reveal cross-project session existence.
- The v2 browser does not bootstrap the legacy PostgreSQL session.

## Execution authority

Only `ExecutionEngine.requestExecution` creates a session. It rechecks the task and exact approved snapshot server-side. Changed spec hash, executor, model, effort, reviewer, or permissions invalidates approval and returns the task to `PENDING_APPROVAL`. Approval does not queue work by itself.

Only the engine changes `ExecutionSession` status. FakeExecutor returns typed events and a validated result; prose cannot mark success. Terminal sessions are immutable.

## Workspace ownership

Project paths are revalidated as canonical Git roots before request and claim. A partial unique SQLite index permits one active workspace writer. Lease renewal requires the random token. Stale recovery requires expired ownership and stale heartbeat evidence, blocks the uncertain session, releases its lease, and audits the recovery. There is no normal force unlock.

## Output

The dependency-free local-safety package redacts output before database previews, SSE, or artifacts. Environment files and credentials are not read. Artifact paths are generated below app-owned storage, never inside project source. Fake changed-file entries are simulated metadata.

## Codex process boundary

- API routes create durable requests or read diagnostics; they never import `child_process` or launch Codex directly.
- Only `packages/relay-v2-execution/src/process-runner.ts` imports `node:child_process`.
- Executables and workspaces are canonical absolute paths; argv is an array; `shell` is always false.
- Task content is stdin, not a command argument. Model/effort flags are emitted only for verified supported selections.
- Environment inheritance is limited to OS execution, PATH, user-profile authentication, temp, terminal/locale, and approved Codex configuration. Secret-like keys are denied and environment values are never logged.
- Output is redacted before events, SSE, diagnostics, or artifacts.
- Windows cancellation targets the exact owned PID tree; Relay never kills by process name or reattaches from PID alone.
- Pre-spawn cancellation is checked before/through validation and around spawn. A termination failure retains process ownership and the workspace lease until exit rather than reporting a false completed cancellation.
- Codex diagnostics responses use an explicit DTO. Raw executable paths remain server-side; browser/API responses expose only sanitized `displayPath` values.
- Dirty-baseline evidence protects staged, unstaged, untracked, index, stash, HEAD, and branch identity. Suspected loss or concealment of pre-existing work blocks success.

## Dependency isolation

Automated transitive graph tests cover the v2 packages, API routes, libraries, app routes, and Relay v2 UI components. They ensure these sources cannot reach legacy execution, provider SDKs, workers, Redis, BullMQ, cross-spawn, MCP, or external API endpoints. They prove `node:child_process` is reachable only from SafeProcessRunner and not UI/API sources. Display labels are not treated as integrations.

Runtime-host operational diagnostics contain only bounded, redacted error messages; stack traces are not retained. Callback failures cannot break polling. A known owned session is identified for diagnostics, while engine cleanup or conservative stale recovery owns its durable lifecycle.

FakeExecutor:

- runs entirely in-process;
- has `writeCapability=false`;
- makes no external API call;
- starts no process or shell;
- performs no Git, Docker, or project filesystem mutation.

Legacy execution remains present and recoverable but was not changed by Milestone 2.

## Review authority (Milestone 2.3A/2.3B)

Only `ReviewEngine` changes `ReviewRequest` status. A reviewer never gains authority merely by being registered: `resolveReviewerAuthority` independently checks that the task approval used for the execution is `APPROVED`, that its reviewer selection is not `NONE`, that the task's current reviewer selection still matches the approval snapshot, and that the requested reviewer id matches what the approved selection resolves to. `PRODUCTION_REVIEWER_ID_BY_SELECTION` maps only `CLAUDE -> "claude-cli"` (still no `CODEX` entry), so `claude-cli` can produce an `AUTHORITATIVE` verdict for a `codex-cli` execution *only* when that execution's task was approved with reviewer selection `CLAUDE`; `fake-reviewer` still cannot produce an `AUTHORITATIVE` verdict for anything — only two narrow, separately-gated `DIAGNOSTIC` paths exist for it: a `FakeExecutor` diagnostic session (engine flag + explicit per-request `diagnostic: true`), and a Codex test-double session in the disposable Playwright browser-test environment (`PROJECT_RELAY_TEST_MODE` + `RELAY_V2_FAKE_REVIEWER_DIAGNOSTIC` + the `playwright-v2` data directory, mirroring the existing Codex process test-double gate exactly). Every review's `reviewAuthority` (`AUTHORITATIVE`/`DIAGNOSTIC`) is bound into its `requestHash`, persisted immutably once terminal, and a `DIAGNOSTIC` verdict can never satisfy a future auto-commit gate — there is no upgrade path, and an `AUTHORITATIVE` `claude-cli` verdict cannot satisfy one either (Milestone 2.3B has no auto-commit policy, same as 2.3A).

A review request cryptographically binds, at request time, to one canonical `ReviewInputCapsule` — every stored execution evidence and reviewer-authority field (spec hash, approval id/status/reviewer-selection snapshot, executor id, capsule, baseline/final Git evidence, verification results, artifact set, final branch/HEAD, review authority) **plus** live-read task title/objective/context, execution status/summary, and two independent spec-integrity recomputations (`canonicalTaskSpecHash` against the approval's embedded spec, `taskNormalizedSpecHash` against the task's current `normalizedSpecJson`) — persisted verbatim as `reviewInputJson`/`reviewInputHash`. **The reviewer's own configuration is bound too, not only the evidence capsule**: for FakeReviewer, `reviewerConfigJson` (outcome/delay/summary/findings/required-actions) directly controls the verdict, so it is validated against a per-reviewer schema, canonicalized, and hashed into `reviewerConfigHash`, persisted alongside `reviewerConfigJson`. `requestHash = sha256(canonicalJson({ reviewInputHash, reviewerConfigHash, reviewerId, reviewAuthority, requestedBy, attempt, reviewPolicyVersion }))` binds both hashes together with the request's authority/administrative identity. The execution capsule hash is never trusted from a single column: it is independently recomputed from the capsule's own self-referential embedded hash and required to match the stored column. `Reviewer.review()` receives exactly the object parsed back from the persisted `reviewInputJson`, plus the object parsed back from the persisted `reviewerConfigJson` — never task/execution fields reassembled from live rows at run time, and never an unbound reviewer configuration, so a title/objective/summary/scenario change can neither reach the reviewer unbound nor drift after the hash is computed.

`ReviewEngine` never trusts a persisted hash merely because the database protects it (below): it independently re-parses, re-validates, and re-hashes `reviewInputJson` and `reviewerConfigJson` and reconstructs `requestHash` from scratch, both immediately before the reviewer is ever invoked and again inside the finalization transaction. A mismatch at either point — a corrupt, imported, or legacy row — transitions the request straight to `STALE` with `failureCode: "REVIEW_IMMUTABLE_INPUT_MISMATCH"`, the reviewer is never called, and no verdict is ever inserted. Immediately before a verdict is persisted, in the same database transaction as the terminal status CAS and the `ReviewVerdict` insert, the engine additionally re-reads every source-of-truth row fresh, re-runs eligibility, spec-integrity, and authority resolution, and reconstructs the full `ReviewInputCapsule` — any live-evidence change (including task title/objective/context/normalized-spec drift) moves the request to `STALE` with `failureCode: "EVIDENCE_CHANGED"` (with the specific reason recorded) instead of accepting the verdict — the two failure codes are kept distinct so the audit trail always records whether the binding itself was corrupted or evidence simply moved on. A terminal request can never be updated again (SQLite trigger, not just application logic), and neither can the authority/evidence/binding payload of a non-terminal one — a second SQLite trigger, `ReviewRequest_immutable_payload`, rejects any change to `reviewInputJson`/`reviewInputHash`/`reviewerConfigJson`/`reviewerConfigHash`/`requestHash`/`reviewerId`/`reviewAuthority`/every evidence hash/identity field in *every* status (`PENDING`/`CLAIMED`/`RUNNING`/`CANCELLATION_REQUESTED` included), permitting only the controlled lifecycle/lease columns to change. `ReviewVerdict` and `ReviewEvent` are append-only, enforced both by SQLite triggers and — for `ReviewVerdict.reviewRequestId` specifically — a database-level `UNIQUE` constraint, so a second verdict for the same review request fails at the database regardless of how it is attempted, independent of the application-level CAS. A structurally invalid or hash-mismatched reviewer response becomes `ERROR`, never `APPROVE`.

Cancellation and verdict finalization race safely: cancelling a claimed/running review is a compare-and-swap `UPDATE ... WHERE status IN (...)` into a durable `CANCELLATION_REQUESTED` state committed *before* the in-process abort signal fires, and verdict/error/stale finalization is a matching CAS scoped to the exact claimed ownership generation (`ownerId`, `leaseToken`, `claimAttempts`, live `leaseExpiresAt`) — exactly one of the two can ever win, and the loser's write is dropped, never a partial or duplicate terminal outcome. Every terminal write re-proves that ownership generation is still live immediately before writing: an expired lease (heartbeats stopped, or the owner paused) or a superseded claim generation (reclaimed by recovery or a new owner) can never produce a verdict — only `recoverStaleReviews` or a still-live owner's own race-resolution path may touch an ownerless row, and an expired owner is never revived. API routes never invoke a reviewer directly; they only create a `PENDING` row, and a durable `ReviewRuntimeHost` atomically claims (`CAS PENDING -> CLAIMED` with an owner id, lease token, claim-attempt counter, and heartbeat-renewed expiry) and runs it, so a crashed request or restarted process can never strand or silently drop a review — an expired lease recovers conservatively to `CANCELLED` (if cancellation was already requested) or `STALE` (otherwise), and no verdict is ever invented during recovery.

A review verdict changes only a separately computed `ReviewGateProjection` (`state`/`authority`/`reviewerId`/`reviewRequestId`/`verdictId`/`requestHash`/`commitAuthorityEligible`) — never a plain status string, so a `DIAGNOSTIC` `APPROVE` is always visibly diagnostic in every API response and UI surface, and never a plain `ExecutionSession`/`Task` status mutation, Codex reopen/rerun, file modification, or Git operation. `commitAuthorityEligible` and `canSatisfyAuthoritativeReviewGate` unconditionally return `false`/deny in this milestone — there is no auto-commit policy yet, so no caller can derive commit authority from `verdict === APPROVE` alone, AUTHORITATIVE or not. `fake-reviewer` and `claude-cli` are the only two registered reviewers. `fake-reviewer` is read-only and fully in-process (no filesystem/network/process access at all); the `relay-v2-reviewer` package itself depends only on `relay-v2-domain`, `relay-v2-persistence`, `local-safety`, and `zod` and cannot import `SafeProcessRunner` or `node:child_process`, which dependency-isolation tests enforce directly. `claude-cli` lives in the separate `relay-v2-claude-reviewer` package (the only place besides `relay-v2-execution`'s own `SafeProcessRunner` boundary that this whole codebase permits to reach a real subprocess for v2) — see `docs/CLAUDE_REVIEWER.md` for its full safety model: no workspace, no tools, no MCP, no hooks, no session persistence, a disposable bundle outside the Relay repository, live re-verification of CLI identity/authentication immediately before every invocation, and structured-output validation that never trusts the process's own exit code or prose.

### Milestone 2.3B corrective pass

An independent Codex security review of the first Milestone 2.3B implementation returned **REJECT**. The corrective pass (see `docs/CLAUDE_REVIEWER.md` for full detail) fixed every finding:

- Claude now receives actual bounded, redacted evidence content (Git diff, changed-file status, verification stdout/stderr, constraints, acceptance criteria, an artifact manifest) as part of `ReviewInputCapsule` — the original implementation bound only hashes of that evidence, which is insufficient for an authoritative code review regardless of how strong the hash-binding is.
- `reviewMaterialHash`/`promptHash` are now computed and bound *before* the Claude process is spawned, and the verdict must echo both (plus `reviewedRequestHash`) — verified independently before any verdict is accepted.
- The Claude CLI's stdout is parsed strictly (no Markdown-fence stripping, no prose-surrounded-JSON recovery, no picking between duplicate JSON objects) against an exact transport-wrapper shape verified from a real, sanitized `claude.exe` v2.1.220 invocation (an earlier pass had only modeled this shape from an unrelated pre-existing stream parser, never a real `-p --output-format json` capture — that gap is closed; see `docs/CLAUDE_REVIEWER.md`'s "Structured output"). The wrapper's `result` and `structured_output` fields must independently parse to, and canonically agree on, the same verdict — a mismatch is `ERROR`, never a verdict resolved by trusting one field over the other. Telemetry fields the wrapper carries (session/uuid/usage/cost/timing/fast-mode state) are validated for shape only and never used as verdict authority, logged, persisted, or exposed. The production parser never falls back to a bare, unwrapped verdict shape on failure; that shape is reachable only through the triple-gated Playwright/CI process test double, never from a real invocation. Unknown/differently-shaped future wrapper versions fail closed under the same strict schema rather than being silently accepted.
- `RELAY_V2_CLAUDE_PATH` no longer authorizes an arbitrary existing file: the resolved candidate must be a canonical absolute regular file with the expected basename and, on Windows, a structurally valid native PE header.
- Every capability flag the real invocation unconditionally relies on is mandatory (UNKNOWN is never treated as supported); a live capability-set drift (not just executable identity/version) blocks a review; and the id/diagnostic-content pairing for a capability snapshot is read from one atomic query, closing a race that could previously bind a request to mismatched snapshot content.
- Sanitized diagnostic display paths never leak a raw absolute path, drive root, username, or organization/project folder name.
- `ReviewInvocation` is a lease-owned lifecycle (`PREPARING` through a terminal status) durably coupled to heartbeat/ownership, not a single forensic write made after the fact — heartbeat loss now actually aborts the owned process, and a runtime-restart-recovered non-terminal invocation quarantines its execution session from a new authoritative request rather than being silently forgotten.
- The 2.3B migration's `ReviewRequest` table rebuild is now wrapped in an explicit transaction (sqlite.org's documented atomic-ALTER-TABLE recipe), and migration tests prove both a clean data-preserving upgrade and a full rollback on a deliberately injected mid-migration failure.

A **second** independent Codex review of that corrected pass again returned **REJECT** (two blockers, two high-risk findings). This second corrective pass fixed:

- `ReviewInvocation` is now database-enforced `UNIQUE(reviewRequestId)` — exactly zero or one row per review request, created atomically together with its ownership re-check (previously two separate, non-transactional steps with a narrow TOCTOU gap) — replacing the earlier append-only, unbounded-row-count model.
- The Claude CLI's supported versions are now an explicit, exact catalog (`wrapper-contract-catalog.ts`), not implied only by flag/help detection — an unobserved patch release is unsupported and blocked before any process is spawned, closing a gap where capability discovery could have authorized a version whose wrapper shape was never actually verified. (`2.1.221` was later registered alongside `2.1.220`, but only after an operator-run structural diagnostic proved its real wrapper identical; `2.1.222` and every other unobserved version remain unsupported.)
- Malformed non-empty persisted Git/verification evidence (syntactically valid JSON but the wrong shape, or genuinely non-parseable) is now a hard eligibility failure, never silently degraded to an "unavailable"/empty evidence summary that a review could otherwise proceed past.
- The 2.3B migration's `PRAGMA foreign_key_check` — which only ever returns a result set and can never itself abort a script — is now backed by a real SQLite `CHECK` constraint that does abort the transaction on any actual violation; proven against the real `prisma migrate deploy` path with a seeded dangling foreign key, not by SQL string inspection.

A **third** independent Codex review of that second corrective pass again returned **REJECT** (one blocker, three high-risk findings, plus a test gap). This third corrective pass fixed:

- Persisted Git/verification evidence is now validated against **strict, fail-closed schemas** mirroring the actual production writers (`.strict()` Zod schemas in `review-binding.ts` for `workspace-evidence.ts`'s `GitEvidence`/`GitEvidenceDelta` and `verification-catalog.ts`'s `VerificationResult`), including self-referential hash re-verification, a PASS-with-nonzero-exit refinement, duplicate/conflicting changed-path rejection, and traversal-path rejection — a value like `{ "unexpected": true }` is now a hard schema failure, not merely "not `{}`, so treat as unavailable."
- **Byte-level artifact validation** (`artifact-evidence.ts`) reads every required `ExecutionArtifact` (execution log, final Git evidence/diff, verification results) directly from the application-owned artifact store and independently re-verifies session ownership, bound-artifact-set membership, canonical path containment (no absolute-path injection, `..` traversal, or symlink/junction escape), regular-file-ness, byte count, and SHA-256 before any of it is trusted as review evidence — never falling back to the live project/Relay workspace. This runs both at request time and again at pre-verdict revalidation.
- A heartbeat call that **throws** is now caught and treated identically to a `false` return (ownership loss, owned process aborted) through one idempotent guard, closing a gap where a throwing heartbeat could produce an unhandled rejection and leave the process unsupervised.
- `ReviewInvocation` now durably transitions `PREPARING` → `RUNNING` the instant the real process starts (a CAS re-proving invocation id, ownership generation, and live lease), persisting the real process identity — previously the row stayed `PREPARING` for the entire process lifetime, so a crash mid-review was indistinguishable from one that never started.
- `wrapperContractId`/`wrapperParserVersion` are now bound durably through capability snapshot, diagnostic, semantic hash, persisted capability row, reviewer config, config hash, and `ReviewInvocation`, with an independent live re-check immediately before every spawn — a deployment remapping the same CLI version string to a different verified contract can no longer reuse an existing request or spawn under a stale binding.
- The foreign-key migration regression test now seeds a genuine orphan directly in an unmodified 2.3A database (foreign keys disabled on one setup connection only) and runs the unchanged, checked-in 2.3B migration against it, rather than injecting corruption into a copy of the migration script.

A **fourth** hardening pass (not itself in response to an independent review — closing three limitations that pass's own completion report had explicitly flagged, ahead of the next independent review) fixed:

- **AUTHORITATIVE review now requires a configured, readable, byte-validated artifact store as a real assertion, not a silently-skippable condition.** The prior gate was a bare `if (session.executorId === "codex-cli" && this.artifactsRoot)` inside eligibility — if `artifactsRoot` was ever unset for an engine that otherwise reached this code path, byte-level artifact validation was silently skipped rather than blocking. It is replaced by `ReviewEngine.validateAuthoritativeArtifactEvidence`, keyed on the resolved `reviewAuthority` and enforced at three points — request time (before any `ReviewRequest` row exists), a live pre-spawn re-check immediately before the reviewer is ever invoked, and pre-verdict revalidation — with absence or a read/hash failure always reported as `ERROR`, distinct from ordinary evidence drift (`STALE`).
- **A central, versioned `AuthoritativeReviewMaterialBudget`** replaces a set of independent, uncoordinated per-field caps with one explicit aggregate/per-category byte budget, deterministically accounted from the actual assembled `ReviewInputCapsule` (UTF-8 byte length, fail-closed on overflow), enforced at request time and revalidation, plus an independent final check on the exact rendered stdin bytes immediately before the reviewer CLI is spawned. A duplicate artifact-manifest entry is now rejected outright, so no category can evade the budget by splitting content across many entries.
- **An explicit, enforced, three-tier category truncation policy** (non-truncatable-critical / truncatable-critical-with-disclosure / optional) replaces what was previously a documentation-only policy constant nothing in `ReviewEngine` actually consulted. A truncated final Git diff that no longer evidences every changed file, a failed verification operation whose truncated output cannot be proven to preserve its failure-relevant tail, and a critical field that collapsed to near-nothing under secret redaction are now all hard-blocked rather than silently presented as incomplete evidence.
- **The `LOG` artifact's real, validated bytes now actually reach Claude.** Byte-level artifact validation always read and hash-verified every required artifact's content, but every prior caller discarded it, keeping only a pass/fail result — nothing in the review pipeline ever consumed the validated bytes for the one evidence category (`LOG`, the execution's own event transcript) that had no other representation in the material at all. The same validated `Buffer` is now embedded, head+tail bounded and disclosed, directly into the capsule — never re-read a second time — closing the gap between "bytes were validated" and "bytes were actually used."

See `docs/CLAUDE_REVIEWER.md`'s "A fourth independent corrective pass" and "Central material byte budget enforcement", and `docs/REVIEW_ENGINE.md`'s "Eligibility" section, for full detail.

### Milestone 2.3B fifth corrective pass: artifact bytes as the authoritative source

The previous pass validated artifact bytes and then discarded them, rendering the review from database JSON that vouched for itself with its own embedded hash. That is not a security property: an actor who can rewrite that JSON can also recompute the hash inside it, so nothing tied the content shown to Claude to the content whose bytes had been validated.

- **Versioned, strict artifact contracts.** `FINAL_GIT`, `PATCH`, `CHANGED_FILES`, `VERIFICATION`, and `LOG` each have a `.strict()`, versioned schema in `packages/relay-v2-domain/src/evidence-artifacts.ts`. Unknown, renamed, or added fields are hard parse failures; an unsupported `schemaVersion` is rejected outright. The contracts live in the domain package so producer and consumer are held to the *same* definition, not to two copies that can drift.
- **One cryptographic equality edge.** Artifact bytes are read from the application-owned store, ownership- and membership-checked, containment- and regular-file-checked, byte-count- and SHA-256-verified, strictly decoded, schema-parsed, canonicalized, and hashed. The database JSON must reduce through the *same* canonical semantics to a byte-identical value before it may be rendered. Divergence in **either** store blocks the review before any reviewer process is spawned and before any `ReviewVerdict` can exist.
- **Producer truncation is truthful and blocking.** Original/included/omitted byte counts and the full-content hash are computed at write time from the complete content, before any cut. The schema cannot express "nothing was lost" and "bytes are missing" simultaneously. Producer-truncated `FINAL_GIT`/`PATCH`/`CHANGED_FILES`/`VERIFICATION` blocks an AUTHORITATIVE review; the reviewer never reconstructs missing source content. An upstream capture that lost an unknown amount is reported as `captureTruncated`, not as a fabricated count.
- **Conditional evidence requirements.** A changed set requires both a changed-file artifact and a covering final patch; an empty change set requires an explicit, valid, empty changed-file artifact. Absence is never read as emptiness, a baseline patch never stands in for a final one, and conflicting statuses or duplicate normalized paths are rejected.
- **Strict UTF-8 and binary policy.** Authoritative evidence is decoded with `TextDecoder` in `fatal` mode, never permissive `Buffer.toString("utf8")`. Invalid UTF-8, NUL bytes, disallowed C0/C1 control bytes and DEL, binary content, and a leading BOM are all rejected. Hashes are taken over the **original raw bytes**, never a decoded/re-encoded string — the two diverge exactly when decoding was lossy.
- **Code-point-safe redaction and truncation.** Redaction runs first, the redacted bytes are measured, then truncation cuts only on complete Unicode code-point boundaries — never a `Buffer` slice that can split a multibyte sequence or a surrogate pair. Omission-marker bytes are charged against the render budget first and counted toward the rendered size; omitted bytes are reported against the complete redacted source.
- **Exact byte accounting, bound and re-proved.** An exact serialized ledger measures every rendered section with the real serializer; the prompt and stdin are built once and measured from the built strings. `maxPromptBytes` and `maxFinalStdinBytes` are enforced independently. The ledger's policy version and canonical hash are bound into the `ReviewRequest` (covered by its immutable-payload trigger) and into the `ReviewInvocation`, and are reconstructed and required to match before any verdict is accepted. Any difference is `STALE`/`ERROR` with no verdict, and Claude is never rerun.

### Milestone 2.3B sixth corrective pass: what is measured is what is sent, and what is sent is what is judged

An independent Codex review of the fifth pass again returned **REJECT** (three blockers, three high-risk findings). Each closed a gap between a check and the thing the check was supposed to be about:

- **Runner-level output loss can no longer be recorded as complete.** `SafeProcessRunner` counts every byte a process writes but stops forwarding once its combined cap is reached; `VerificationCatalogRunner` read only `exitCode` from the exit event, so a run whose output was thrown away could persist as an empty stream, `captureTruncated: false`, and `PASSED` — evidence asserting that a command which printed megabytes printed nothing. The runner's own `outputTruncated`/`stdoutBytes`/`stderrBytes` now propagate into per-stream `StreamCaptureProvenance` with an end-to-end byte chain and an explicit `COMPLETE`/`TRUNCATED_KNOWN`/`TRUNCATED_UNKNOWN` completeness. Unknown loss is represented as unknown — never guessed, and never hashed from the surviving fragment — and **blocks** an AUTHORITATIVE review regardless of exit status. An empty capture with nonzero raw bytes cannot be recorded as legitimate empty output.
- **The material ledger now measures the exact envelope that is transmitted.** Previously the ledger summed separately serialized fragments while a *different* object was sent (outer framing, nested framing, property names, separators, escaping, `requestHash`), and the manifest and ledger were hashed into the binding but never placed inside the material Claude could read. There is now one versioned transmitted value, `ReviewMaterialEnvelopeV1 { schemaVersion, core, ledger }`, built in a strictly ordered, non-self-referential sequence, canonicalized **once**; `maxTotalIncludedBytes` is enforced against those exact bytes, `reviewMaterialHash` is taken over them, and the manifest, provenance disclosure, and ledger are inside what the reviewer receives.
- **Identities are persisted before the process starts.** The complete transmitted identity — envelope version, budget policy version, ledger JSON and hash, `reviewMaterialHash`, exact envelope byte count, prompt policy version, `promptHash`, prompt/stdin byte counts, and `finalStdinHash` — is written on the `PREPARING` `ReviewInvocation` row inside the same transaction that proves ownership, before Claude exists, and is **write-once** at the database level. The reviewer sends those exact prepared bytes and builds nothing of its own.
- **Finalization independently reconstructs everything.** The engine rebuilds the capsule, envelope, ledger, prompt, and stdin from current evidence and compares field by field against the bound invocation, then requires Claude's echoed hashes to match that reconstruction rather than its own input. Evidence drift is `STALE`; a mismatched binding or echo is `ERROR`. Nothing reruns.
- **Pre-spawn reconstruction stops a doomed run before it starts.** Evidence rewritten *coherently* after the request (both stores valid, self-hashes recomputed) is caught before any invocation row is created and before Claude is invoked — not after paying for a review whose verdict would have to be discarded.
- **LOG evidence is record-structured and provenance-carrying.** The producer writes a complete NDJSON record or none at all (never a half-written object), and its versioned `LogProvenance` — complete-stream hash, byte counts, record counts, completeness — travels to the reviewer unchanged, as one immutable validated part, from artifact validation through the capsule, the material envelope, the provenance disclosure, the byte ledger, and the invocation identities, and is cross-checked against the real bytes at each of request, pre-spawn, and finalization. Every included record must parse as exactly one schema-valid JSON object; a partial trailing line, a JSON array, or an unknown record shape is refused. An AUTHORITATIVE review requires that provenance: absent, `{}`, malformed, `TRUNCATED_UNKNOWN`, or self-contradicting provenance blocks before any invocation row is created and before Claude is started, and provenance that drifts after the request invalidates the review instead of producing a verdict. The artifact row and the producer provenance are also required to describe **one identical stream** — byte counts, truncation flag and method, hashes, and record counts must all agree, since two individually valid records that contradict each other about the same log are not evidence about the run. That pair is refused as `LOG_PROVENANCE_ARTIFACT_MISMATCH`, with no representation preferred, inferred, or normalized.
- **Diff coverage is proven from parsed file headers.** `unifiedDiff.includes(path)` counted a filename appearing anywhere — including inside another file's hunk body — as coverage. Coverage now comes from exact `diff --git`/`---`/`+++`/rename headers only, with malformed headers, quoted paths, traversal paths, duplicate conflicting blocks, and blocks whose rename metadata contradicts their own `diff --git`/`---`/`+++` paths all refused; the same parser runs on the producer, the schema, the database projection, and the reviewer, so the stores cannot disagree by classifying differently.

## Planned

An auto-commit gate (Milestone 2.4), broader operation-risk catalogs, dedicated dangerous-operation approvals, secure API credentials, and MCP remain later work. Automatic Git mutation and deployment are not present — not even for an AUTHORITATIVE Claude APPROVE.
